# Blipark iOS App — 正式產品架構與核心 UX 流程實作計畫

## 0. 任務背景與目標

Blipark 是一款以「目的地停車規劃」與「停車引導」為核心的 App。

使用者可以事先規劃目的地附近的停車策略，或在出發前臨時搜尋目的地，查看周邊可選擇的停車場與路邊停車格，並在行車過程中取得停車引導。

目前已有一個 iOS POC App，驗證過部分技術與互動效果，包括：

- Picture in Picture（PiP）顯示導航資訊。
- 地圖、導航路線、旋轉與位移等渲染。
- 設定目的地與候選停車點。
- 部分導航模擬、定位及相關測試功能。
- 不同 PiP 渲染方式與導航呈現策略。

這些功能的效果目前已達到相對可接受的程度。

接下來希望以既有專案為基礎，逐步建立正式產品的 UI、資料架構與完整使用流程。

### 本次實作的核心目標

1. 建立正式 App 的主要資訊架構與頁面。
2. 實作目的地搜尋、停車探索、停車策略配置及儲存計畫。
3. 實作首頁「下一個計畫」與開始計畫流程。
4. 將既有 PiP／導航 POC 的成熟功能整合到正式流程。
5. 建立獨立的測試資料管理功能，支援手動建立真實地點的測試情境。
6. 透過統一的資料介面，讓正式 UI 不依賴 Mock Data 的實作方式。
7. 讓使用者可以完整體驗從搜尋目的地到開始停車引導的 UX。

本階段最重要的是：

**正式使用流程必須完整、自然，並且能夠使用測試資料實際操作，而不是單純建立一組靜態 UI Demo。**

# 1. 開發原則與工程要求

## 1.1 優先遵循既有專案架構

開始修改前，請先檢查現有 iOS 專案：

- 專案目錄與模組結構。
- 使用的 Swift／SwiftUI／UIKit 架構。
- 現有資料模型與狀態管理方式。
- 既有 PiP、地圖、定位、導航相關實作。
- POC 功能之間的相依關係。
- 可重複使用的元件與服務。
- 目前的測試與建置方式。

實作時：

- 優先沿用已經成熟且合理的設計。
- 不要無必要地重新實作已完成的 POC 功能。
- 不要為了符合新的目錄結構而進行大規模重構。
- 如果既有架構存在明顯問題，可以局部改善。
- 新增功能應盡可能避免與既有 POC 形成緊密耦合。

如果需要重構既有功能，請確保原本可以運作的 POC 不會受到破壞。

## 1.2 架構設計原則

遵循常見軟體工程原則：

- Separation of Concerns
- Single Responsibility Principle
- Dependency Inversion
- Interface／Protocol-based Design
- Dependency Injection
- Testability
- Maintainability
- Extensibility

以現有專案的技術架構為基礎，採用適度的分層。

如果目前使用 SwiftUI，可以優先考慮：

- View：負責畫面呈現與互動。
- ViewModel／Feature State：管理畫面狀態與操作。
- Domain Models：表示核心業務資料。
- Use Cases／Services：處理停車策略、推薦、計畫啟動等業務邏輯。
- Repositories／Providers：抽象化資料存取。
- Infrastructure／Integrations：實作本機資料、未來 API、MapKit、PiP、定位等。

不強制套用完整 Clean Architecture，也不要引入大量沒有必要的抽象層。

**目標是清楚、容易理解、方便測試與擴充，而不是為了架構而架構。**

## 1.3 資料來源必須可替換

目前沒有正式的停車資料 API，因此先以本機測試資料代替。

但正式畫面不可直接依賴：

- 硬編碼的 Mock Array。
- 測試資料管理頁面。
- 特定 JSON 格式。
- 測試專用 ViewModel。
- 測試資料的儲存實作。

應透過清楚定義的 Repository／Provider 取得資料。

未來接入正式 API 時，應主要修改：

1. API Client。
2. API Response DTO。
3. DTO 與 Domain Model 的 Mapping。
4. 對應的 Repository 實作。
5. 必要的錯誤處理與快取策略。

正式 UI、停車策略、計畫管理與導航流程不應因此需要大幅重寫。

由於正式 API Schema 尚未確定，目前只需定義合理的 Domain Contract，不需要猜測 API 的 Endpoint 或 Response 格式。

# 2. App 的核心產品概念

Blipark 有兩個核心功能：

1. 目的地停車規劃。
2. 停車點引導。

地圖導航與 PiP 是輔助呈現方式，並不是獨立的主要功能。

使用者大致有三種情境。

## 2.1 已經儲存計畫

使用者事先規劃好目的地、停車候選與偏好。

出發時：

首頁 → 選擇計畫 → 開始計畫 → 選擇引導模式 → 出發。

## 2.2 臨時搜尋目的地

使用者直接搜尋目的地，或匯入 Google Maps／Apple Maps 連結。

接著：

搜尋 → 目的地 → 周邊停車探索 → 調整停車策略 → 儲存計畫或直接出發。

## 2.3 熟悉目的地路線，只需要停車引導

使用者知道最終目的地怎麼走，不需要 Google Maps 或 Apple Maps 提供完整導航。

但他仍需要知道目的地附近有哪些停車點，以及如何前往候選停車點。

這種情況：

- 不需要開啟外部地圖。
- 不需要使用 PiP。
- 直接停留在 Blipark。
- 接近目的地後顯示停車候選與引導。
- 如果目前候選無法停車，可以切換下一個候選。

注意：

**這兩種引導模式共用相同的停車計畫、候選停車點與策略。差異只在顯示方式。**

不要把它們設計成兩個完全不同的核心功能。

# 3. 正式 App 資訊架構

## 3.1 Bottom Tab Bar

第一版使用三個主要 Tab：

### Home — 首頁

主要負責快速開始行程。

包含：

- 下一個／最近的停車計畫。
- 搜尋目的地入口。
- 匯入地圖連結入口。
- 進行中的停車引導（如果有）。
- 少量次要快捷功能。

### Plans — 計畫

管理使用者已儲存的停車計畫。

包含：

- 計畫列表。
- 計畫詳情。
- 編輯計畫。
- 停車候選及順序。
- 開始計畫。
- 刪除計畫。

### Profile — 我的

放置個人資訊與較少使用的功能。

包含：

- 預設車種。
- 全 App 通用停車偏好。
- 歷史紀錄入口。
- App 設定。
- 開發者／測試資料管理入口（僅測試環境）。

第一版不需要將「地圖」、「附近停車」或「導航」做成獨立 Tab。

## 3.2 非 Tab 的功能頁面

以下頁面由主要流程進入：

- 目的地搜尋。
- 目的地周邊停車探索。
- 停車點詳情。
- 停車策略配置。
- 計畫詳情／編輯。
- 出發確認。
- App 內停車引導。
- 開發者測試資料管理。

頁面導覽方式可以使用：

- NavigationStack。
- Sheet。
- Bottom Sheet。
- Full-screen presentation。

請依照 iOS 常見 UX 模式選擇，不要所有操作都強制跳轉完整頁面。

# 4. 首頁實作

## 4.1 設計目標

首頁最明顯的兩個入口必須是：

1. 已儲存計畫。
2. 搜尋目的地。

不要讓歷史紀錄、附近停車或其他次要功能搶走主要操作的視覺焦點。

整體設計希望：

- 簡潔。
- 清楚。
- 容易閱讀。
- 主要操作明顯。
- 資訊不要過度擁擠。
- 符合 iOS 原生使用習慣。

視覺風格可以採用 Blipark 的藍綠色系與適度的雷達意象，但不要過度使用裝飾。

## 4.2 下一個計畫卡片

首頁有已儲存計畫時，顯示「下一個計畫」。

資訊包含：

- 目的地名稱。
- 目的地簡短位置。
- 預計出發日期／時間（如果有）。
- 使用車種。
- 候選停車點數量。
- 主要停車偏好摘要。
- 第一候選停車點（如果有）。
- 「開始計畫」主要按鈕。

互動：

- 點擊卡片內容 → 計畫詳情。
- 點擊「開始計畫」→ 出發確認 Bottom Sheet。
- 有多個計畫時，可滑動或切換卡片。
- 點擊「所有計畫」→ Plans Tab。

不需要將完整地圖或所有候選停車點塞進首頁卡片。

## 4.3 計畫排序

初版採用簡單且容易預期的排序：

1. 有指定未來出發時間的計畫，依時間排序。
2. 沒有指定時間的計畫，依最近使用／修改時間排序。
3. 過期但未執行的計畫仍然保留，不自動標記完成。

不需要實作複雜的智慧排序。

## 4.4 沒有儲存計畫

顯示適當的 Empty State。

讓搜尋目的地成為主要操作。

可以簡單說明：

「搜尋目的地，開始規劃附近的停車方式。」

不要為了填滿首頁而新增大量不必要的功能卡片。

## 4.5 有進行中的計畫

如果目前有進行中的停車引導：

- 首頁最上方顯示進行中的行程卡片。
- 顯示目的地與目前候選停車點。
- 提供「繼續停車引導」。
- 不要要求重新建立計畫或重新設定偏好。

# 5. 目的地搜尋與停車探索

這是本次最重要的正式 UX 流程之一。

## 5.1 搜尋入口

從首頁可以：

- 搜尋地點名稱。
- 搜尋地址。
- 貼上 Google Maps／Apple Maps 地點連結。
- 選擇最近搜尋。
- 選擇預存目的地。

如果部分外部連結格式尚未支援，應有明確的錯誤或未支援狀態，不要假裝已成功解析。

## 5.2 AutoComplete

目前以測試資料為主。

當使用者輸入關鍵字時：

1. 查詢符合條件的預存測試目的地。
2. 優先顯示這些目的地。
3. 如果現有地點搜尋功能可使用，也可以顯示一般地點搜尋結果。
4. 避免重複顯示同一個地點。
5. 選取後進入目的地探索頁。

可以另外提供「最近目的地」。

注意：

- 不要在正式搜尋畫面顯示 Mock／Test 標籤。
- 測試目的地使用穩定的 ID 與座標識別。
- 不要只透過地點名稱字串比對資料。
- 測試情境尚未建立時，提供合理的 Empty State。
- 一般搜尋結果如果沒有對應停車資料，不可以自動產生虛假的停車點。

## 5.3 目的地周邊停車探索頁

使用者選擇目的地後，進入主要的停車探索畫面。

建議採用：

**地圖＋底部可展開停車點列表。**

地圖顯示：

- 最終目的地。
- 周邊停車場。
- 路邊停車點／路段。
- 當前選取的停車候選。

清單顯示：

- 停車點名稱。
- 停車類型。
- 總格位數（資料有提供時）。
- 距離目的地的距離。
- 步行距離或時間（可取得時）。
- 是否收費。
- 費率摘要（若已知）。
- 推薦順序或優先級。

地圖與清單應互相連動。

例如：

- 點擊地圖上的停車點 → 清單選中對應項目。
- 點擊清單項目 → 地圖聚焦對應停車點。
- 展開清單 → 可以比較更多資訊。

如果步行路線尚未計算，請明確標示為直線距離或約略距離，不要當成實際步行距離。

## 5.4 停車點詳情

可以顯示：

- 名稱。
- 位置。
- 停車類型。
- 總格位數。
- 收費資訊。
- 與目的地距離。
- 備註。
- 地圖位置。

如果既有 MapKit／Look Around 功能方便整合，可以加入環景查看。

但環景功能不是本階段的阻塞項目。

沒有支援的地點應正常顯示不可使用狀態。

## 5.5 停車資訊的重要限制

目前資料主要是靜態資料。

例如：

「總共有 30 個停車格」

不等於：

「現在還有 30 個空位」。

因此：

- 不要顯示虛構的即時剩餘車位。
- 不要使用「目前有位」等無依據的說法。
- 不要以總格位數推斷實際空位。
- 資料未知時應顯示未知，而不是自動填 0。
- 將停車點稱為「候選停車點」，而不是保證有位可停。

未來可以新增即時剩餘位資料，但目前不需要實作。

# 6. 停車策略系統

## 6.1 設計目標

使用者不一定知道該如何選擇停車點。

因此 App 應有一套全域預設停車策略。

當使用者沒有自行設定時，直接使用這套策略推薦與排序停車候選。

如果使用者有自己的需求，可以進行調整。

## 6.2 初版策略項目

先支援少量核心條件：

- 車種。
- 停車類型偏好（停車場／路邊格位／不限）。
- 是否偏好免費停車。
- 最大可接受步行距離。
- 距離優先。
- 手動指定候選順序。

不需要一開始就建立複雜的評分系統。

可以先採用簡單、可解釋、可測試的推薦規則。

例如：

1. 排除不符合車種或明確限制的停車點。
2. 依使用者偏好排序。
3. 優先考慮較接近目的地的候選。
4. 使用穩定的次要排序條件，避免結果反覆變動。

未知的收費、格位數等資料不能直接當作免費、零格位或已滿。

如果使用者指定步行距離上限，但目前只有直線距離，應避免將兩者混為同一條件。

## 6.3 全域策略與計畫策略

請區分：

### Global Strategy

整個 App 通用的預設策略。

可以在「我的 → 停車偏好」設定。

### Plan Strategy

特定計畫使用的策略。

預設可以繼承全域策略；使用者也可以修改成計畫專屬設定。

### Manual Candidate Order

使用者自行指定的停車候選順序。

這應與自動推薦策略區分。

例如使用者指定：

A → C → B

則開始計畫時應尊重這個順序，不應被自動推薦排序重新覆蓋。

建議清楚定義繼承、覆寫與重新排序的規則。

## 6.4 策略 UI

初版提供簡單易懂的設定即可。

例如：

- 停車類型。
- 收費偏好。
- 步行距離。
- 推薦排序。
- 手動調整候選順序。

不需要一開始就提供大量權重滑桿。

如果某些策略尚未決定實際演算法，可以先不顯示，或標註尚未支援。

不要放一個看似有效、實際卻不影響推薦結果的設定。

# 7. Plan 系統

## 7.1 Plan 的定位

Plan 是使用者自己儲存的停車規劃。

它不是測試資料，也不是 API 回傳的停車資訊。

一份 Plan 至少包含：

- Plan ID。
- 計畫名稱（可預設目的地名稱）。
- 最終目的地。
- 使用車種。
- 選取的停車候選。
- 停車候選順序。
- 使用的停車策略。
- 預計出發時間（選填）。
- 建立與更新時間。

## 7.2 建立計畫

從目的地探索頁可以：

- 使用系統推薦候選。
- 自行調整停車候選。
- 修改偏好。
- 儲存成 Plan。

儲存成功後，應能在 Plans Tab 中找到。

如果使用者沒有設定時間，也可以儲存。

## 7.3 計畫詳情

顯示：

- 目的地。
- 出發時間（如果有）。
- 地圖。
- 候選停車點與順序。
- 停車策略摘要。
- 編輯功能。
- 開始計畫。

此頁不需要包含開發者測試資料編輯功能。

## 7.4 Plan 與資料來源的關係

Plan 應保留使用者自行設定的內容。

例如：

測試資料包含 5 個停車點。

使用者選擇其中 3 個，並手動排序。

之後如果測試資料中的停車資訊更新，不應自動把使用者的候選順序覆蓋。

請設計清楚的參照與必要的資料快照機制。

至少確保：

- Plan 不會因測試資料更新而意外損壞。
- 刪除測試資料時不會造成 Crash。
- 已儲存 Plan 的候選資訊可以合理恢復。
- 未來切換 API Provider 後，Plan 仍能處理資料 ID 改變或來源暫時不可用的情況。

# 8. 開始計畫與停車引導流程

## 8.1 啟動入口

以下兩種來源應共用同一套啟動流程：

1. 首頁／Plans Tab 中的已儲存 Plan。
2. 搜尋目的地後直接出發。

直接出發不應強制要求先儲存成 Plan。

兩者最後都應建立一個正式的停車引導 Session。

## 8.2 出發確認

使用者點擊「開始計畫」或「直接出發」後，顯示簡短的 Bottom Sheet。

包含：

- 目的地名稱。
- 候選停車點數量。
- 使用車種。
- 必要的策略摘要。
- 引導模式選擇。

提供兩種模式。

### Mode A：搭配外部地圖導航

使用者選擇：

- Google Maps。
- Apple Maps。

流程：

1. 建立停車引導 Session。
2. 準備 PiP 導航與停車引導所需資料。
3. 開啟外部地圖前往最終目的地。
4. 由 Blipark 的 PiP 顯示停車引導資訊。
5. 接近目的地後，依既有 POC 能力提供更詳細的停車引導。

注意：

PiP 是否能在背景持續更新、是否能自動啟動或調整視窗比例，應遵循現有 POC 實際驗證結果與 iOS 系統限制。

不要假設所有 PiP 視窗行為都能自由控制。

### Mode B：只使用 Blipark

使用者不需要外部地圖導航。

流程：

1. 建立停車引導 Session。
2. 留在 Blipark。
3. 進入 App 內引導頁面。
4. 在行駛過程中追蹤目的地接近狀態。
5. 接近目的地後，提供候選停車點引導。
6. 無法停車時，允許切換下一個候選。

初版可以重用現有 POC 的地圖與路線渲染能力。

不需要從零開始打造完整的 Google Maps／Apple Maps 替代品。

## 8.3 兩種模式共用核心邏輯

應共用：

- 目的地。
- 候選停車點。
- 停車策略。
- 候選順序。
- Session 狀態。
- 接近目的地判定。
- 目前正在引導的候選點。
- 切換下一候選點的邏輯。

不同模式只負責呈現方式與外部整合。

## 8.4 引導 Session

建議獨立定義 ParkingGuidanceSession。

至少包含：

- Session ID。
- 目的地。
- 候選停車點順序。
- 目前候選 Index。
- 引導模式。
- 開始時間。
- Session Status。

Session Status 可以包含：

- Preparing。
- Active。
- Paused。
- Completed。
- Cancelled。
- Failed。

不需要讓 Session 與 Plan 使用同一個資料模型。

Session 可以來自 Plan，也可以來自臨時搜尋。

應避免重複點擊開始按鈕時意外建立多個 Active Session。

## 8.5 候選停車點切換

使用者如果發現目前候選沒有位置：

可以切換到下一個候選。

這裡只代表：

「使用者認為此候選無法停車，因此改往下一個候選。」

不能直接推斷停車場已滿，也不要將其寫成所有使用者共享的即時剩餘位資訊。

初版先支援手動切換。

不需要建立依賴即時空位資料的自動切換系統。

行車畫面應盡量減少必須手動操作的步驟。

## 8.6 暫停、恢復與結束

至少需要：

- 開始 Session。
- 恢復 Active Session。
- 結束 Session。
- 返回 App 後繼續查看。

如果既有 POC 沒有完整的背景 Session 恢復能力，請先完成可用的基本版本，並清楚記錄目前的限制。

不要為了實作 Session 而大幅破壞既有 PiP 功能。

# 9. 獨立測試資料管理工具

這部分非常重要。

目前沒有正式停車 API，所以需要測試人員自行建立真實地點附近的停車資料，來測試完整 UX。

但是：

**測試資料管理 UI 與正式產品 UI 必須完全分離。**

## 9.1 入口

建議在 Debug／Internal Testing 環境中提供：

「我的 → 開發者工具 → 測試資料管理」

也可以沿用既有 POC App 的獨立測試區塊。

請依專案架構選擇最合適的方式。

要求：

- 一般正式流程不出現測試資料編輯功能。
- 正式搜尋與停車探索不出現 Mock／Test 標籤。
- 測試環境可以方便進入資料管理工具。
- 正式發布版本不應意外暴露測試資料管理入口。
- 如果正式 API 尚未完成，正式環境應提供誠實的服務未開放狀態，而不是偷偷使用測試資料。

## 9.2 測試資料的概念

測試資料不是 Plan。

它代表：

「某個目的地附近，可以取得哪些停車點資訊。」

例如：

Dataset A：

目的地：台南美術館

停車點：

- 停車場 A。
- 路邊格位 B。
- 停車場 C。
- 路邊格位 D。

這些資料模擬的是未來 API 所提供的內容。

使用者透過正式畫面搜尋台南美術館後，才會依策略選擇候選並建立自己的 Plan。

## 9.3 測試資料管理頁

至少支援：

- 查看已建立的測試情境。
- 新增測試情境。
- 編輯測試情境。
- 刪除測試情境。
- 查看該情境包含多少停車點。
- 啟用／停用測試情境（若有需要）。

每組測試情境包含：

- Destination。
- 多個 ParkingLocation。
- 選填的描述或備註。

## 9.4 新增目的地

測試者應可以：

- 搜尋地點。
- 透過地圖選擇位置。
- 輸入地址。
- 在必要時手動調整座標。

建議優先利用現有 MapKit 能力。

不要要求測試者一定要自行查詢經緯度才能建立目的地。

## 9.5 新增停車點

測試者可以在目的地周邊新增多個停車點。

至少需要：

- 名稱。
- 停車類型。
- 地理位置。
- 車種。
- 總格位數（選填）。
- 是否收費（可為未知）。
- 收費資訊（選填）。
- 備註（選填）。

新增位置時，建議支援：

- 地圖點選。
- 地點搜尋。
- 手動輸入座標。

如果是路邊停車格，初版可以使用代表點或簡單路段資料。

但資料模型應保留未來支援 LineString／路段幾何的可能性。

## 9.6 本機儲存

測試資料必須持久化。

重新開啟 App 後仍然存在。

可以依現有架構選擇：

- SwiftData。
- Core Data。
- SQLite。
- Versioned JSON Storage。

優先使用現有專案已採用的持久化方式。

不要只把測試資料放在記憶體 Array。

## 9.7 匯入與匯出

如果實作成本合理，建議加入 JSON 匯入／匯出。

用途：

- 分享測試情境。
- 備份資料。
- 在不同 Simulator／實體手機間搬移。
- 提供自動化測試使用。

匯入時應檢查：

- Schema Version。
- 必要欄位。
- ID 重複。
- 座標是否合法。
- 格位數是否合法。
- 無法解析的資料。

遇到無效資料時，不應直接讓 App Crash 或覆蓋既有資料。

## 9.8 不要建立假的使用者 Plan

開發者建立一組測試目的地時：

只代表資料來源新增了一個目的地及其周邊停車點。

不應自動建立使用者 Plan。

Plan 必須透過正式使用流程自行儲存。

這樣才有辦法完整測試真實 UX。

# 10. Domain Models 與資料介面

請先盤點現有 Model，再決定哪些可以沿用。

以下是預期需要的核心概念。

## 10.1 Destination

表示最終目的地。

建議欄位：

- id
- name
- address?
- coordinate
- externalPlaceId?
- metadata?

## 10.2 ParkingLocation

表示停車場或路邊停車地點。

建議欄位：

- id
- name
- type
- coordinate／geometry
- supportedVehicleTypes
- totalSpaceCount?
- chargingInfo?
- pricingInfo?
- notes?
- sourceMetadata?

ParkingType 至少包含：

- ParkingLot
- OnStreet

對於未知的可選資料使用 Optional 或明確的 Unknown 狀態。

不要將未知資訊硬轉成 0、false 或空字串。

## 10.3 ParkingStrategy

表示使用者的停車偏好。

包含：

- vehicleType
- preferredParkingTypes
- pricingPreference
- maximumWalkingDistance?
- sortingPreference
- 其他未來可擴充設定

具體欄位可以依實作需求調整。

## 10.4 ParkingPlan

表示使用者已儲存的計畫。

包含：

- id
- name
- destination
- scheduledDepartureAt?
- strategy／strategyOverride
- selectedCandidateIds
- manualCandidateOrder?
- createdAt
- updatedAt

## 10.5 ParkingGuidanceSession

表示一次實際開始的停車引導。

包含：

- id
- destination
- orderedCandidates
- currentCandidateIndex
- guidanceMode
- status
- startedAt
- updatedAt

## 10.6 TestDataset

表示一組測試用目的地與停車點資料。

包含：

- id
- schemaVersion
- destination
- parkingLocations
- createdAt
- updatedAt

TestDataset 與 ParkingPlan 必須分開。

# 11. Repository 與 Provider 設計

希望達到以下依賴關係：

正式 View
    ↓
ViewModel／Use Case
    ↓
Repository／Provider Protocol
    ↓
Mock／Local Repository 或 Future API Repository

至少需要區分：

## 11.1 Destination Search

負責搜尋與解析目的地。

支援：

- 搜尋預存目的地。
- 依 ID 取得目的地。
- 未來接入地點搜尋服務。
- 必要時解析外部地圖連結。

## 11.2 Parking Data Provider

負責取得目的地附近的停車資訊。

例如：

- 根據目的地位置查詢停車點。
- 根據條件篩選。
- 取得停車點詳情。

這個介面應是正式 UI 的主要資料入口之一。

## 11.3 Plan Repository

負責儲存使用者 Plan。

包含：

- 建立。
- 讀取。
- 更新。
- 刪除。
- 列表查詢。

Plan Repository 不應與 Mock Parking Provider 混為一體。

## 11.4 Strategy Repository

負責儲存全域偏好。

停車推薦計算應在獨立 Service／Use Case 中完成。

不要直接將推薦規則寫死在 View 裡面。

## 11.5 Guidance Session Repository／Service

負責建立及維護進行中的停車 Session。

由正式使用流程呼叫，再將資料交給既有引導系統。

## 11.6 Developer Test Data Repository

專門負責：

- 新增測試情境。
- 編輯測試情境。
- 儲存測試資料。
- 匯入／匯出。
- 資料驗證。

它可以與 Mock Parking Provider 使用相同的底層資料儲存，但不應讓正式 UI 直接依賴它。

# 12. 既有 PiP／導航 POC 整合

## 12.1 保留既有成果

現有 POC 中成熟的功能應盡量沿用。

包括：

- PiP 顯示。
- 地圖渲染。
- 路線顯示。
- 地圖旋轉與位移。
- 導航模擬。
- 已驗證的定位與背景行為。

不要求將整個 POC 重寫成新架構。

## 12.2 抽離測試參數輸入

原本 POC 可能透過測試頁面手動輸入：

- 目的地。
- 停車點。
- 行進路線。
- 渲染參數。
- 模擬速度等。

正式流程應改為：

1. 從 Plan／搜尋取得目的地。
2. 從 Parking Provider 取得停車資料。
3. 套用停車策略。
4. 建立 Guidance Session。
5. 將 Session 資料交給既有引導元件。

既有 POC 測試頁面仍可保留，但不要成為正式流程的必要步驟。

## 12.3 建立適配層

如果現有導航元件需要特定資料格式，請考慮建立 Adapter。

例如：

Domain Guidance Session
    ↓
Navigation／PiP Adapter
    ↓
Existing POC Renderer

不要讓正式 Plan Model 直接依賴 POC 渲染器的內部資料結構。

這樣未來替換或改善渲染方式時，較不會影響正式 UI。

## 12.4 定位來源

如果目前已有模擬定位能力，應保留在測試環境。

正式引導可以使用定位 Provider 抽象。

例如：

- DeviceLocationProvider
- SimulatedLocationProvider

但不要讓使用者在正式畫面中看到測試定位選項。

定位權限被拒絕、位置不可用時，應顯示合理狀態，不要假裝定位正常。

# 13. UI／UX 實作規範

## 13.1 優先完成合理的使用體驗

本次不用追求所有畫面都已經是最終設計。

但是主要流程應該：

- 互動自然。
- 資訊層級清楚。
- 操作一致。
- 有適當的 Loading／Empty／Error State。
- 不會因沒有資料造成整個畫面崩潰。
- 符合 iOS 常見操作習慣。

## 13.2 建立可重用 UI 元件

例如：

- PlanCard
- DestinationSearchField
- ParkingLocationCard
- ParkingTypeBadge
- ParkingSummary
- StrategyPreferenceView
- DepartureConfirmationSheet
- EmptyStateView

元件名稱及拆分可以依實際架構調整。

不要過度抽象化，也不要為每個小圖示都建立獨立元件。

## 13.3 不確定的功能不要硬做

如果某些功能尚未決定，例如：

- 完整歷史紀錄。
- 計畫分享。
- 智慧出發提醒。
- 複雜的推薦權重。
- 自動判斷停車場是否已滿。
- 特定環景整合。
- 進階導航模式切換。

目前不需要強行完成。

可以：

1. 暫時不顯示。
2. 使用明確 Disabled State。
3. 標註 Coming Soon。
4. 留下簡短 TODO。

但不要建立看似可用、點擊後卻沒有任何反應的按鈕。

## 13.4 視覺設計

建議：

- SwiftUI 原生風格。
- 清楚的卡片與資訊層級。
- 適當的留白。
- 藍綠色作為品牌主色。
- 停車資訊使用一致的圖示與標籤。
- 支援深色／淺色模式（若成本合理）。
- 注意 Dynamic Type 與基本無障礙標籤。

避免：

- 過度複雜的動畫。
- 不必要的漸層與裝飾。
- 每個畫面使用不同設計語言。
- 把所有設定直接塞在首頁。
- 用測試功能填滿空白區域。

## 13.5 行車安全

停車引導介面應盡量降低駕駛操作負擔。

優先呈現：

- 目前目標停車點。
- 必要的轉向或路線提示。
- 下一個候選。
- 簡短且清楚的狀態。

複雜的策略設定、排序與資訊比較應在出發前完成。

不要要求駕駛在行進中頻繁操作手機。

# 14. 建議的實作階段

請採取增量開發，不要一次大量重寫整個專案。

## Phase 1 — 專案盤點與基礎架構

- 檢查既有專案。
- 找出可重用 POC 元件。
- 建立正式 App Navigation 架構。
- 定義 Domain Models。
- 定義 Repository／Provider Protocols。
- 建立需要的依賴注入方式。
- 確認本機資料持久化方案。

驗收條件：

- 專案可以正常建置。
- 原有 POC 仍可使用。
- 正式 App 的主要頁面可以正常切換。
- 核心資料介面已明確定義。

## Phase 2 — 測試資料管理

- 建立 TestDataset Model。
- 建立本機測試資料持久化。
- 實作測試情境列表。
- 實作目的地選擇。
- 實作停車點新增／編輯。
- 實作地圖選點。
- 實作資料驗證。
- 可行時支援 JSON 匯入／匯出。

驗收條件：

- 可以建立一個真實目的地。
- 可以手動新增多個附近停車點。
- 資料重新啟動後仍然存在。
- 可以修改與刪除資料。
- 正式 UI 不會出現測試資料編輯控制項。

## Phase 3 — 正式搜尋與停車探索

- 實作目的地搜尋。
- AutoComplete 優先顯示符合條件的預存目的地。
- 選擇目的地後，從 Provider 取得停車資料。
- 實作地圖與停車點清單。
- 實作基本停車點詳情。
- 實作基本篩選與排序。

驗收條件：

- 可以在正式畫面搜尋 Phase 2 建立的目的地。
- 可以查看它周邊的測試停車點。
- 地圖位置正確。
- 清單與地圖互動正常。
- 沒有資料時能正常顯示 Empty State。

## Phase 4 — 停車策略與 Plan

- 建立全域預設策略。
- 實作基本推薦排序。
- 支援手動調整候選順序。
- 支援儲存 Plan。
- 實作 Plans Tab。
- 實作計畫詳情與編輯。
- 實作首頁下一個計畫卡片。

驗收條件：

- 可以從搜尋結果建立 Plan。
- 可以修改計畫候選與偏好。
- 可以儲存多個計畫。
- 首頁可以看到下一個計畫。
- 關閉 App 後仍可取得已儲存計畫。
- 更改 TestDataset 不會無故覆蓋 Plan 個人設定。

## Phase 5 — 開始計畫與導航整合

- 實作出發確認 Bottom Sheet。
- 支援兩種引導模式。
- 建立 Guidance Session。
- 整合既有 PiP POC。
- 整合 App 內停車引導。
- 支援候選切換。
- 支援 Session 恢復與結束。

驗收條件：

- 已儲存 Plan 可以開始引導。
- 臨時搜尋可以不儲存直接出發。
- 兩種模式使用同一套候選資料。
- 正式流程不需要進入 POC 測試頁面。
- 既有 PiP 功能沒有因整合而明顯退化。
- 使用者可以返回 App 查看進行中的引導。

## Phase 6 — 測試與整理

- 進行完整 User Flow 測試。
- 補齊基本單元測試。
- 檢查主要 Empty／Loading／Error State。
- 檢查資料持久化。
- 檢查導航與 POC 整合。
- 移除不必要的暫時性程式碼。
- 補充必要文件。

# 15. 測試要求

## 15.1 Unit Tests

至少涵蓋：

- 停車資料驗證。
- 停車策略排序。
- 未知／缺失資料處理。
- Plan 建立及更新。
- Plan 與 TestDataset 的資料隔離。
- Guidance Session 狀態轉換。
- 候選停車點切換。
- Repository 的基本行為。

## 15.2 Integration Tests

至少測試：

1. 建立 TestDataset。
2. 正式搜尋找到目的地。
3. 取得停車資料。
4. 套用策略。
5. 儲存 Plan。
6. 從首頁開始計畫。
7. 建立 Guidance Session。
8. 將資料交給既有引導元件。

測試時應可注入 Fake Repository，不需要依賴真實外部 API。

## 15.3 UI／Manual Tests

至少驗證以下流程：

### Scenario A：事先規劃

建立測試目的地 → 搜尋 → 查看停車點 → 調整策略 → 儲存 Plan → 回首頁 → 開始計畫。

### Scenario B：臨時出發

搜尋目的地 → 查看停車候選 → 不儲存 → 直接出發。

### Scenario C：只需要停車引導

選擇目的地 → 只使用 Blipark → 接近目的地 → 查看候選 → 切換下一個候選。

### Scenario D：外部地圖＋PiP

選擇目的地 → 搭配地圖導航 → 啟動現有 PiP 引導流程。

### Scenario E：資料修改

建立測試資料 → 建立 Plan → 修改測試資料 → 確認 Plan 個人設定沒有被意外覆蓋。

### Scenario F：異常情況

- 沒有測試資料。
- 停車點資料不完整。
- 地點搜尋失敗。
- 定位權限被拒絕。
- Plan 參照的停車點不存在。
- 使用者中途離開引導畫面。
- App 重新啟動後恢復資料。

# 19. Codex 執行指示

請直接以目前 Repository 為基礎進行實作。

開始前先完成專案盤點，確認現有架構與 POC 能力，並依照專案實際情況調整上述技術細節。

不需要完全照搬建議的類別名稱或目錄結構。

如果現有專案已有合理的設計，應優先沿用。

執行時請遵循：

1. 優先確保既有 POC 正常運作。
2. 以小範圍、可驗證的變更逐步完成各階段。
3. 先確立資料模型與介面，再實作依賴它們的正式畫面。
4. 對已經明確的功能直接實作，不必反覆詢問。
5. 對尚未定案的功能採用簡單的 Placeholder／Coming Soon，不需要自行擴充大量需求。
6. 不要因為目前使用 Mock Data，就建立一次性的正式 UI 架構。
7. 遇到平台限制或既有 POC 尚不支援的行為，應採用合理的降級方案並清楚記錄。
8. 優先完成端到端可操作流程，而不是先花大量時間完成所有非核心畫面的視覺細節。
9. 每完成一個主要階段，盡可能執行 Build／Tests，並修正發現的問題。
10. 不要宣稱未驗證的功能已經完成。

如果所有階段無法一次完成，請優先完成 Phase 1～4，確保正式搜尋、停車探索、策略配置與 Plan 可以完整運作，再繼續整合 Phase 5。

完成後請提供：

- 實際完成的功能摘要。
- 主要架構與資料流說明。
- 新增或修改的重要檔案。
- Build／Tests 結果。
- 仍未完成或受到限制的功能。
- 實際操作與驗證完整 User Flow 的方式。

請以能長期維護的正式產品程式碼品質為目標，而非一次性的 POC Demo。
